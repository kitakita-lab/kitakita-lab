# harness-sync — 共通ハーネスの展開と点検

正本と仕組みは `harness/README.md`。このファイルは手順だけを書く。マージ・Draft の解除はしない（共通ルール「人間だけが行うこと」）。

## 1. 対象を探す（状況の確認）

1. `list_repos` で KitaKita Lab のリポジトリを一覧する。
2. 各リポジトリの `main` の `AGENTS.md` を GitHub から読み、`<!-- BEGIN:kitakita-harness` を含むものを「導入済み」とする。
3. 導入済みのリポジトリだけを `add_repo`（push）→ `git clone --depth 1` し、このリポジトリで
   `npm run harness:sync -- status <フォルダ> ...` を実行する。

## 2. 更新する（古い版があるとき）

リポジトリごとに次を行う。1 つで止まっても、他のリポジトリは続けてよい。

1. 開いている PR に `claude/harness-sync` ブランチのものがあれば、そのブランチを使う（新しい PR を作らない）。なければ最新 `main` から作る。
2. `npm run harness:sync -- apply <フォルダ>`。「書き換えない（手で変更）」なら、そのリポジトリは止めて報告する（固有の事情をブロックの外へ移すかは人間が決める）。
3. 変更が管理ブロックと `CLAUDE.md` の `@AGENTS.md` の 1 行だけであることを `git diff` で確かめる。変更がなければ何もしない。
4. そのリポジトリの検査を手元で実行する（`AGENTS.md`・`CLAUDE.md`・`docs/harness.md` に書かれたもの。pre-commit フックがあれば有効にして commit する）。
5. commit・push し、Draft PR を作る（本文はそのリポジトリの PR テンプレートに従う。共通ルールの差分の要約と、正本の commit を書く）。
6. そのリポジトリの手順に従って Codex レビューを依頼する（`gate:codex-wait` があればそれを使う）。

## 3. 導入する（人間が依頼したときだけ）

`npm run harness:sync -- apply <フォルダ> --add common`（視覚的な制作があれば `--add common,creative`）。以降は 2 の 3〜6 と同じ。
自動の点検（予約）では導入しない。

## 4. 記録する

- Notion の状況ボードの子ページ「共通ハーネス｜運用方針とプロジェクトの入口」の展開状況の表を、`status` の結果と PR のリンクで更新する
  （その表の範囲だけを範囲指定で書き換える。ページ全体の置き換えはしない）。接続できなければ「Notion 未反映」と報告して続ける。
- 公開リポジトリ（このリポジトリを含む）の PR・Issue には、非公開リポジトリの名前と PR の一覧を書かない。

## 5. 報告する

日本語で、結論から。リポジトリごとの状態（最新 / 更新 PR を作成 / 手で変更のため停止 / 未導入）と PR のリンク、人間がマージすべき PR を書く。
変更がなかった場合は「変更なし」とだけ報告し、PR・Notion の記録を作らない。
