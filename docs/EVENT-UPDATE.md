# 実績更新ハーネス（実施報告書 PDF ＋ 写真 → 本番公開）

イベント実績（`/events/<slug>`）を 1 件追加し、本番公開まで進めるための手順と判定基準。
**このファイルに書いた範囲の作業だけ**、条件がそろえば個別の承認を待たずにマージ・公開まで進めてよい。
条件が一つでも欠けたら止めて報告する（推測で進めない、合格扱いにしない）。

---

## 0. 対象範囲

自動で公開してよい変更は次だけ。

| ファイル | 内容 |
|---|---|
| `src/data/events.ts` | 実績 1 件の**追加**（既存の実績は変更しない） |
| `src/data/news.ts` | 「〜を開催しました」1 件の追加 |
| `public/events/<slug>/*.jpg` | 新しい実績の写真 |
| `public/sitemap.xml` | ビルドで再生成される差分（新しい URL の追加）だけ |

これ以外のファイルが変わる場合（コンポーネント・デザイン・既存の実績やトップの文言・数値の更新など）は、
通常の PR として作成して止め、ユーザーの判断を待つ。
例: トップや `/workshop` の「2026年6月から9月にかけて…6会期」は期間を区切った記述なので、実績を追加しても書き換えない。
書き換えが必要だと考えたら、提案として報告する。

## 1. ユーザーから受け取るもの

1. 実施報告書 PDF（一次資料）
2. 掲載用の写真（「3. 写真」の条件）
3. 任意: 載せない情報・使わない写真の指示

## 2. 報告書から使う情報・使わない情報

報告書はクライアント向けの文書で、そのまま公開する前提で書かれていない。実績紹介に必要な情報だけを再構成する。

| 使う | 使わない |
|---|---|
| 会期・曜日・開催時間・会場 | 提出先（「〜 御中」）・取引先や主催企業の名称・契約条件・金額 |
| イベント名（企画名）・実施ブランド・KitaKita Lab の担当範囲 | 担当者名・連絡先 |
| ワークショップの参加組数・参加人数・制作数（総数・日別） | イベント全体の成果（来場者数・売上・集客数）への読み替え |
| 天候・時間帯の傾向・制作時間の目安 | 「次回へのご提案」など運営改善の提案 |
| 客層の傾向・会場の様子（個人が特定できない範囲で、報告書の記述どおり） | 参加者の発言の**直接引用**（公開許可を確認できない限り。要旨に言い換える） |
| 現場の所感（「〜と感じています」と、事実と分けて書く） | 他の会期との比較で成果を大きく見せる表現・報告書にない数字やエピソード |

数字のルール:

- 報告書の数字と一致させる。総数は日別の合計と一致すること（`events.test.ts` が検算する）。
- 報告書で「約」「概算」「目測」とある数字は、断定に書き換えない。
- 「イベント全体」と「ワークショップ（報告対象）」を混同しない。報告書の「報告対象」欄で確認する。

## 3. 写真

| 用途 | 枚数 | 比率・書き出し | 推奨する内容 |
|---|---|---|---|
| ヒーロー（`hero`） | 1 | 16:9・1600×900（横位置） | ブースと制作の様子が一枚で伝わるもの |
| スマホ用ヒーロー（`hero-mobile`） | 0〜1 | 1:1・1000×1000 | ヒーローが縦位置で、横長に切ると伝わらない場合だけ |
| フォトギャラリー | 4 | 4:3・1200×900 | 会場全景／制作の手元／花材や完成品／ブランドの展示や季節の要素 |

- 受け取る形式: JPEG・PNG・WebP（HEIC は先に JPEG へ変換）。長辺 2000px 以上が望ましい。
- 書き出し: `npm run photos:prepare -- <slug> hero=<元画像>:16x9 venue=<元画像> ...`
  （規格サイズに切り抜き、500KB 以下、EXIF・位置情報を除去。`@x%,y%` で切り抜きの中心を指定）

公開可否（AI が判断し、迷ったら止める）:

- 参加者の顔が判別できる写真は、公開の同意が確認できない限り使わない。お子さまは特に慎重に。
- 名札・個人名・車のナンバー・他社のロゴや掲示物の権利に注意する。スタッフの顔も本人の同意が前提。
- 生成画像・仮画像を開催写真として使わない。写真がそろわなければ公開しない。

## 4. 実装

1. 最新の `main` から `events/<slug>` ブランチを作る。slug は `<会場>-<年>[-<月>]`（例: `ario-sapporo-harvest-court-2026-10`）。
2. `src/data/events.ts`: 直近の同種の実績（2026年9月の 3 件）をひな形にする。
   - `overview`（イベント名・実施内容・実施ブランド・会期・会場・企画・運営）
   - `stats` 4 件（総参加組数・総参加人数・フラワーボトル制作数・開催日数）
   - `sections` 4〜5 件（イベント概要／ワークショップ内容／その会期の特徴 1〜2／KitaKita Lab としての所感）
   - `dayReports`（各日の「N組・N名…N本」で始める）・`photos` 4 件
   - `voices`（発言の引用）は使わない
3. `src/data/news.ts`: 「〜で〜を開催しました」を 1 件。`date` は公開日。
4. 文体は `docs/BRAND.md`。簡潔で具体的に。誇張しない。

## 5. 自動チェック（機械で判定するもの）

| チェック | 実行 | 判定すること |
|---|---|---|
| 型・Lint・テスト・ビルド | `npm run typecheck && npm run lint && npm run test:coverage && npm run build` | CI と同じ。ビルドはページごとの title 重複・meta 重複・本文欠落でも失敗する |
| 公開前チェック（`src/data/events.test.ts`） | 上のテストに含まれる | 画像の実在・500KB 以下・EXIF なし・alt／`dateISO` と会期の一致／日別の合計＝総数／宛先・企業名・メールアドレスを含まない |
| 表示 | `npm run check:visual -- --shots /events/<slug>,/events` | 全ページ × 6 幅（320〜1440px）で横スクロール・読み込めない画像・JS エラーがない。スクリーンショットを保存 |
| 変更範囲 | `git diff --name-only origin/main...HEAD` | 「0. 対象範囲」のファイルだけ |
| CI | `npm run gate:checks -- <PR>` | Quality Checks・Cloudflare Pages（プレビュー）が成功 |
| Codex レビュー | `npm run gate:codex -- <PR>` | 「7.」の条件 |

`check:visual` は外部通信を遮断するため、書体は代替フォントで描かれる（はみ出しの判定には十分。最終的な見た目はプレビュー URL で確認できる環境なら確認する）。

## 6. AI が判断するもの（機械では判定できない）

PR 本文にチェック結果を書く。

- [ ] 本文の各文に報告書の根拠がある（PR に「項目／報告書／サイト」の照合表を付ける）
- [ ] 発言は引用せず要旨にしている。個人が特定できる記述がない
- [ ] 写真の公開可否・トリミング・alt の内容
- [ ] 既存の実績と、情報の粒度・トーンがそろっている
- [ ] スクリーンショット（390px・1440px）を見て、崩れ・写真の切れ方に問題がない

## 7. PR と Codex レビュー

1. PR を作り、本文に照合表・変更ファイル・自動チェックの結果・判断事項を書く。
2. PR に `@codex review` とコメントする。
3. 数分待って `npm run gate:codex -- <PR>` を実行する。
   - **PASS**: 最新の commit を Codex がレビュー済みで、未解決の指摘・スレッドがない
   - **PENDING**: 未実行・実行中・古い commit のレビュー結果しかない → 待つ
   - **FAIL**: 未解決の指摘・スレッドがある
4. 指摘への対応:
   - 再現・妥当性を確認する。妥当なら修正の commit を積み、スレッドに対応内容を返信して解決（resolve）する。
   - 妥当でないと判断した指摘は、理由を返信し、**解決にはせず**止めてユーザーに報告する。
   - 修正したら再び `@codex review` → `gate:codex`。
5. 上限: レビューは 3 回（初回＋再レビュー 2 回）まで。超えたら止める。PENDING が 30 分続いたら止める。

コメントを投稿しただけ、レビューを依頼しただけでは合格にしない。判定は `gate:codex` の結果（Codex が残す
`codex-review-state` の commit・状態・未解決の有無と、レビュースレッド）で行う。

## 8. マージの条件（すべて満たすときだけ）

1. `gate:codex` が PASS
2. `gate:checks` が PASS
3. `check:visual` の問題が 0 件で、スクリーンショットを確認済み
4. 変更ファイルが「0. 対象範囲」の中だけ
5. 報告書との照合に不一致がなく、公開可否を判断できない写真・情報がない
6. コンフリクトがない（`mergeable: true`）

マージは head の commit を指定して行う（確認後に別の commit が積まれた場合に失敗させるため）。

```
gh api -X PUT repos/kitakita-lab/kitakita-lab/pulls/<PR>/merge -f merge_method=merge -f sha=<headのcommit>
```

ブランチ保護や必須チェックが設定されている場合は、それに従う（迂回しない）。

## 9. 本番反映の確認

マージ完了と本番反映は別に確認する。

```
npm run gate:deploy -- <マージcommit> https://www.kitakita-lab.com/events/<slug> --expect "<実績のタイトル>"
```

- **VERIFIED**: Cloudflare Pages のデプロイ成功、公開 URL で新しいページを確認 → 完了
- **DEPLOYED_UNVERIFIED**: デプロイは成功したが、公開 URL を確認できない → 「デプロイ成功・公開 URL 未確認」と報告する（完了とは書かない）
- **FAIL**／**PENDING** が続く → 止めて報告する

Claude Code のクラウド環境では、ネットワーク設定の許可ドメインに `www.kitakita-lab.com` がないと公開 URL を確認できない。

## 10. 止める条件

次のいずれかなら、マージせずに止めて報告する。

- Codex レビューが完了していない／指摘が未解決／Codex が利用できない
- テスト・ビルド・CI の失敗、`check:visual` の問題
- 表示（プレビュー・スクリーンショット）を確認できない
- 報告書と掲載内容に不一致がある、報告書にない情報が必要
- 公開可否を判断できない写真・情報がある、写真が足りない
- 「0. 対象範囲」外のファイルや共通デザインの変更が必要
- 本番デプロイの状態が分からない、権限不足・認証失敗

## 11. 完了報告（短く）

```
実績: <タイトル>（/events/<slug>）
状態: 公開済み（本番 URL で確認）｜デプロイ済み・本番 URL 未確認｜停止（理由）
PR: #<番号>（Codex: PASS／レビュー n 回・指摘 n 件対応）
数字: <組>・<名>・<本>（報告書と一致、日別合計も一致）
写真: <枚数>（EXIF 除去・500KB 以下）
確認: テスト n 件・ビルド・表示 28 ページ × 6 幅 問題 0
スクリーンショット: <保存場所>
要確認: <あれば>
```
