# 実績更新ハーネス（実施報告書 PDF ＋ 写真 → 本番公開）

イベント実績（`/events/<slug>`）を 1 件追加し、本番公開まで進めるための手順と判定基準。
**このファイルに書いた範囲の作業だけ**、条件がそろえば個別の承認を待たずにマージ・公開まで進めてよい。
条件が一つでも欠けたら止めて報告する（推測で進めない、合格扱いにしない）。

---

## 0. 対象範囲

自動で公開してよい変更は次だけ。

| ファイル | 内容 |
|---|---|
| `src/data/events.ts` | 実績 1 件の**追加**（既存の実績は変更しない） |
| `src/data/news.ts` | 「〜を開催しました」1 件の追加 |
| `public/events/<slug>/*.jpg` | 新しい実績の写真 |
| `public/sitemap.xml` | ビルドで再生成される差分（新しい URL の追加）だけ |

これ以外のファイルが変わる場合（コンポーネント・デザイン・既存の実績やトップの文言・数値の更新など）は、
通常の PR として作成して止め、ユーザーの判断を待つ。
例: トップや `/workshop` の「2026年6月から9月にかけて…6会期」は期間を区切った記述なので、実績を追加しても書き換えない。
書き換えが必要だと考えたら、提案として報告する。

## 1. ユーザーから受け取るもの

1. 実施報告書 PDF（一次資料）
2. 掲載用の写真（「3. 写真」の条件）
3. 任意: 載せない情報・使わない写真の指示

## 2. 報告書から使う情報・使わない情報

報告書はクライアント向けの文書で、そのまま公開する前提で書かれていない。実績紹介に必要な情報だけを再構成する。

| 使う | 使わない |
|---|---|
| 会期・曜日・開催時間・会場 | 提出先（「〜 御中」）・取引先や主催企業の名称・契約条件・金額 |
| イベント名（企画名）・実施ブランド・KitaKita Lab の担当範囲 | 担当者名・連絡先 |
| ワークショップの参加組数・参加人数・制作数（総数・日別） | イベント全体の成果（来場者数・売上・集客数）への読み替え |
| 天候・時間帯の傾向・制作時間の目安 | 「次回へのご提案」など運営改善の提案 |
| 客層の傾向・会場の様子（個人が特定できない範囲で、報告書の記述どおり） | 参加者の発言の**直接引用**（公開許可を確認できない限り。要旨に言い換える） |
| 現場の所感（「〜と感じています」と、事実と分けて書く） | 他の会期との比較で成果を大きく見せる表現・報告書にない数字やエピソード |

数字のルール:

- 報告書の数字と一致させる。総数は日別の合計と一致すること（`events.test.ts` が検算する）。
- 報告書で「約」「概算」「目測」とある数字は、断定に書き換えない。
- 「イベント全体」と「ワークショップ（報告対象）」を混同しない。報告書の「報告対象」欄で確認する。

## 3. 写真

| 用途 | 枚数 | 比率・書き出し | 推奨する内容 |
|---|---|---|---|
| ヒーロー（`hero`） | 1 | 16:9・1600×900（横位置） | ブースと制作の様子が一枚で伝わるもの |
| スマホ用ヒーロー（`hero-mobile`） | 0〜1 | 1:1・1000×1000 | ヒーローが縦位置で、横長に切ると伝わらない場合だけ |
| フォトギャラリー | 4 | 4:3・1200×900 | 会場全景／制作の手元／花材や完成品／ブランドの展示や季節の要素 |

- 受け取る形式: JPEG・PNG・WebP（HEIC は先に JPEG へ変換）。長辺 2000px 以上が望ましい。
- 書き出し: `npm run photos:prepare -- <slug> hero=<元画像>:16x9 venue=<元画像> ...`
  （規格サイズに切り抜き、500KB 以下。EXIF・XMP・PNG/WebP のテキストなどのメタデータを残さず、書き出した画像を検査する。`@x%,y%` で切り抜きの中心を指定）
- 画像ごとの調整（必要なときだけ。指定しなければ従来と同じ書き出し）:
  - `*67%` … 切り抜きを寄せる（比率に合う最大の範囲に対する幅。50〜100%）。他社の POP・ロゴなどの写り込みを外すときに使う。
  - `+0.3ev` … 露出の補正（±1ev まで）。黒と白は動かさず中間調を持ち上げ、色相は変えない（`scripts/lib/photo-tone.mjs`）。
  - 例: `hero=<元画像>:16x9*67%@50%,100%`（下寄せで寄せる）、`hero=<元画像>:16x9+0.6ev`
- 明るさの点検: 書き出し時に中央値 L*（CIE の明度。50 が中間の灰色）を表示し、**42 未満なら「暗い可能性」と警告**する。
  公開中のヒーローは `npm run photos:audit` で一覧にできる。警告は判断の材料で、自動では補正しない。
  - 暗いと警告されたら、まず 390px・1440px のスクリーンショットで見え方を確かめる。
  - 補正するなら +0.3ev から 0.1 刻みで試し、中央値が 42 に届く最小の補正にする。白飛び（L* 97 超が 5% 超）や
    不自然な見え方になるなら、補正をやめて別の写真を検討する。補正量は PR に書く（例: +0.6ev、中央値 36.4 → 43.1）。
  - 黒い服・椅子など、被写体そのものが黒い部分の割合（暗部）は参考値。露出の不足とは区別できないので判定には使わない。
- 写り込みの点検: ヒーローは特に、他社のブランド・店舗の POP・価格表示などが目立たないかを確認する。目立つ場合は
  別のカット、または `*n%` と `@x%,y%` で外せる構図を選ぶ。外すと主題（制作の様子）が切れる・画質が落ちる場合は止めて報告する。

公開可否（AI が判断し、迷ったら止める）:

- 参加者の顔が判別できる写真は、公開の同意が確認できない限り使わない。お子さまは特に慎重に。
- 名札・個人名・車のナンバー・他社のロゴや掲示物の権利に注意する。スタッフの顔も本人の同意が前提。
- 生成画像・仮画像を開催写真として使わない。写真がそろわなければ公開しない。

## 4. 実装

1. 最新の `main` から `events/<slug>` ブランチを作る。slug は `<会場>-<年>[-<月>]`（例: `ario-sapporo-harvest-court-2026-10`）。
2. `src/data/events.ts`: 直近の同種の実績（2026年9月の 3 件）をひな形にする。
   - `overview`（イベント名・実施内容・実施ブランド・会期・会場・企画・運営）
   - `stats` 4 件（総参加組数・総参加人数・フラワーボトル制作数・開催日数）
   - `sections` 4〜5 件（イベント概要／ワークショップ内容／その会期の特徴 1〜2／KitaKita Lab としての所感）
   - `dayReports`（各日の「N組・N名…N本」で始める）・`photos` 4 件
   - `voices`（発言の引用）は使わない
3. `src/data/news.ts`: 「〜で〜を開催しました」を 1 件。`date` は公開日。
4. 文体は `docs/BRAND.md`。簡潔で具体的に。誇張しない。

## 5. 自動チェック（機械で判定するもの）

| チェック | 実行 | 判定すること |
|---|---|---|
| 型・Lint・テスト・ビルド | `npm run typecheck && npm run lint && npm run test:coverage && npm run build` | CI と同じ。ビルドはページごとの title 重複・meta 重複・本文欠落でも失敗する |
| 公開前チェック（`src/data/events.test.ts`） | 上のテストに含まれる | 画像の実在・500KB 以下・メタデータなし（JPEG・PNG・WebP の構造をたどり、表示に必要な部分以外があれば不合格。解析できない画像も不合格）・alt／`dateISO` と会期の一致／日別の合計＝総数／宛先・企業名・メールアドレスを含まない |
| 表示 | `npm run check:visual -- --shots /events/<slug>,/events` | 全ページ × 6 幅（320〜1440px）で横スクロール・読み込めない画像・JS エラーがない。スクリーンショットを保存 |
| 変更範囲 | `git diff --name-only origin/main...HEAD` | 「0. 対象範囲」のファイルだけ |
| CI | `npm run gate:checks -- <PR>` | Quality Checks・Cloudflare Pages（プレビュー）が成功 |
| Codex レビュー | `npm run gate:codex-wait -- <PR>` → `npm run gate:codex -- <PR>` | 「7.」の条件 |

`check:visual` はローカル（`dist/`）の確認で、外部通信を遮断するため書体は代替フォントで描かれる（はみ出しの判定には十分）。
結果は `report-local.json` に `target: "local"` として残る。本番の確認（「9.」の `check:production`）とは別のものとして扱い、
ローカルで問題がないことを「本番で確認済み」と書かない。

## 6. AI が判断するもの（機械では判定できない）

PR 本文にチェック結果を書く。

- [ ] 本文の各文に報告書の根拠がある（PR に「項目／報告書／サイト」の照合表を付ける）
- [ ] 発言は引用せず要旨にしている。個人が特定できる記述がない
- [ ] 写真の公開可否・トリミング・alt の内容
- [ ] 既存の実績と、情報の粒度・トーンがそろっている
- [ ] スクリーンショット（390px・1440px）を見て、崩れ・写真の切れ方・暗さに問題がない（補正した場合は補正量と前後の中央値 L*）
- [ ] ヒーローに他社のブランド・POP などの写り込みが目立たない

## 7. PR と Codex レビュー

1. PR を作り、本文に照合表・変更ファイル・自動チェックの結果・判断事項を書く。
2. `npm run gate:codex-wait -- <PR>` を実行する（最長で約 65 分かかるため、バックグラウンドで実行する）。
   - head の commit への依頼がなければ `@codex review` を投稿する（どの commit への依頼かを目印として残す）。
   - **依頼から 30 分**たっても head のレビューが完了しなければ、同じ commit に **1 回だけ**再依頼する。
   - 再依頼からさらに 30 分たっても完了しなければ止める（PENDING のまま終わる。合格扱いにしない）。
   - 終了時に `gate:codex` と同じ判定を行い、PASS=0／FAIL=1／PENDING=2 で終わる。
3. マージの直前に `npm run gate:codex -- <PR>` を実行する。合否はこの結果だけで決める（`codex-wait` は依頼と待機の道具）。
   - **PASS**: 最新の commit を Codex がレビュー済みで、未解決の指摘・スレッドがない
   - **PENDING**: 未実行・実行中・古い commit のレビュー結果しかない
   - **FAIL**: 未解決の指摘・スレッドがある
4. 指摘への対応:
   - 再現・妥当性を確認する。妥当なら修正の commit を積み、スレッドに対応内容を返信して解決（resolve）する。
   - 妥当でないと判断した指摘は、理由を返信し、**解決にはせず**止めてユーザーに報告する。
   - 修正したら再び `gate:codex-wait` → `gate:codex`（新しい commit への依頼は `codex-wait` が投稿する）。
5. 上限:
   - レビューは 3 回まで。回数は「レビューした commit の数」で数える（初回＋修正後の再レビュー 2 回）。超えたら止める。
   - 停滞したときの同じ commit への再依頼は 1 回まで。これはレビュー回数に数えない。
   - 同じ commit への依頼は、手動で投稿したものも含めて数える（2 回あれば `codex-wait` はそれ以上依頼しない）。
   - `codex-wait` は 1 つの PR につき同時に 1 つだけ実行する（投稿の直前にも状態を取り直し、重複して依頼しない）。
   - 30 分は「その commit への最後の依頼の時刻」から数える。依頼がなくても Codex が head のレビューを始めていれば
     （PR 作成時の自動レビューなど）、その開始時刻から数え、依頼を重ねない。
6. 統合の例外（最新 main を取り込んだ後の最終確認）:
   - 上限の 3 回に達した後でも、head が「最新 main の取り込み（競合解消を含む）」だけの merge commit なら、
     最終確認のレビューを **1 回だけ** 依頼できる。`codex-wait` が次をすべて確かめたときだけ依頼する。
     1. head が merge commit で、取り込んだ側が **いまの main の先端** そのもの（取り込んだ後に main が進んだら、取り込み直してから）
     2. merge で変わったファイルが、main 側で変わったファイルに含まれる（競合解消は可。それ以外のファイルの変更は不可）
     3. 取り込む前の commit が Codex にレビュー済み
     4. この PR でまだ統合の例外を使っていない（PR につき 1 回）
   - 例外のレビューで指摘が出たら止める（修正の commit は例外にならず、上限のまま止まる）。人が判断する。
   - 例外のレビューも合否は `gate:codex`（最新の commit の完了・受領・未解決なし）。PASS でなければマージしない。
   - 新しい実装や通常の修正を、取り込みの merge commit に混ぜて例外を使わない（2. で止まる）。
   - 停滞時の再依頼（5. の 1 回）とは別のもの。例外のレビューが停滞した場合の再依頼も 1 回まで。

| 種類 | 数え方 | 上限 |
|---|---|---|
| レビュー回数 | レビューした commit の数 | 3 回（統合の例外で +1 回、PR につき 1 回） |
| 停滞時の再依頼 | 同じ commit への依頼の数 | commit ごとに 1 回（初回＋再依頼で 2 回） |

コメントを投稿しただけ、レビューを依頼しただけでは合格にしない。判定は `gate:codex` の結果（Codex が残す
`codex-review-state` の commit・状態・未解決の有無と、レビュースレッド）で行う。FAIL（未解決の指摘）は再依頼では解消しない。

## 8. マージの条件（すべて満たすときだけ）

1. `gate:codex` が PASS
2. `gate:checks` が PASS
3. `check:visual` の問題が 0 件で、スクリーンショットを確認済み
4. 変更ファイルが「0. 対象範囲」の中だけ
5. 報告書との照合に不一致がなく、公開可否を判断できない写真・情報がない
6. コンフリクトがない（`mergeable: true`）
7. 最新の main との整合を確かめた（main のブランチ保護は「最新の main への追従」を必須にしていないため、手順で確かめる）。
   同時に進めている PR がある場合、後からマージする PR は最新の main を取り込んでテスト・ビルドを通し、
   head が変わったら最新の commit に対して `gate:codex-wait` → `gate:codex` をやり直す（「7.」の統合の例外）。

マージは head の commit を指定して行う（確認後に別の commit が積まれた場合に失敗させるため）。

```
gh api -X PUT repos/kitakita-lab/kitakita-lab/pulls/<PR>/merge -f merge_method=merge -f sha=<headのcommit>
```

ブランチ保護や必須チェックが設定されている場合は、それに従う（迂回しない）。

## 9. 本番反映の確認

マージ完了と本番反映は別に確認する。

```
npm run gate:deploy -- <マージcommit> https://www.kitakita-lab.com/events/<slug> --expect "<実績のタイトル>"
```

デプロイ直後は公開 URL が一時的に 404 を返すことがある（PR #84 で発生）。`gate:deploy` は反映待ちと判断できる状態を
`--wait` 秒（既定 300 秒、15 秒おき）まで再試行してから判定する（`--wait 0` で 1 回だけ）。

| 公開 URL の状態 | 扱い |
|---|---|
| 2xx で `--expect` の文字列がある | 確認できた |
| 404・5xx・429、2xx でも文字列がない、名前解決・接続の失敗 | 反映待ちとして再試行する |
| 403、401・407（認証）、プロキシによる遮断、証明書を検証できない | この環境からは確認できない（再試行しない） |
| それ以外の 4xx | 失敗（再試行しない） |

- **VERIFIED**: Cloudflare Pages のデプロイ成功、公開 URL で `--expect` の文字列を確認 → 完了
- **DEPLOYED_UNVERIFIED**: デプロイは成功したが、公開 URL を確認できない（遮断・認証・期限内に通信できない・`--expect` の指定なし）
  → 「デプロイ成功・公開 URL 未確認」と報告する（完了とは書かない）
- **FAIL**: デプロイ失敗、または期限を過ぎても 404・期待する文字列がない → 止めて報告する
- **PENDING**: 期限を過ぎてもデプロイが完了しない → 止めて報告する

Claude Code のクラウド環境では、ネットワーク設定の許可ドメインに `www.kitakita-lab.com` がないと公開 URL を確認できない。

続けて、本番の表示を確認する。

```
npm run check:production -- --only /events/<slug>,/events,/news/<slug>-report --shots /events/<slug>
```

- 公開 URL を Chromium で直接開き、ローカルの `check:visual` と同じ項目（6 幅の横スクロール・読み込めない画像・
  JS エラー・HTTP 200 以外）を確認する。結果は `report-production.json` に `target: "production"` として残る。
- 読み込んだリソースを種別（document・stylesheet・script・image・font）ごとに数える。公開サイトと Google Fonts だけを
  読み込み、それ以外の外部通信（アクセス解析など）は遮断して「対象外」として一覧にする。
- 終了コード: 0 = 問題なし・表示に関わるリソースをすべて読み込めた／1 = 問題を検出／3 = 問題はないが読み込めない
  リソースがある（一覧のものは本番で検証できていない。報告に書く）
- 証明書: クラウド環境では外部への HTTPS が出口ゲートウェイで中継され、その CA は環境の CA バンドル
  （`SSL_CERT_FILE`。curl・Node が使う）にしかないため、そのままの Chromium では `ERR_CERT_AUTHORITY_INVALID` になる。
  `check:production` は、開くホストごとに openssl で証明書チェーンとホスト名を CA バンドルだけに対して検証し、
  通ったチェーンの CA の公開鍵だけを Chromium に信頼させる。検証できないホストは開けない（＝未検証になる）。
  証明書の検証を無効にする方法（`--ignore-certificate-errors`・`ignoreHTTPSErrors`）は使わない。
- curl で取得した HTML を Chromium に渡す方法は使わない（応答ヘッダーが失われ、外部フォントなどを読み込めず、
  本番の表示を再現できないため）。

## 10. 止める条件

次のいずれかなら、マージせずに止めて報告する。

- Codex レビューが完了していない／指摘が未解決／Codex が利用できない
- テスト・ビルド・CI の失敗、`check:visual` の問題
- 表示（プレビュー・スクリーンショット）を確認できない
- 報告書と掲載内容に不一致がある、報告書にない情報が必要
- 公開可否を判断できない写真・情報がある、写真が足りない
- 「0. 対象範囲」外のファイルや共通デザインの変更が必要
- 本番デプロイの状態が分からない、権限不足・認証失敗
- Codex レビューが、再依頼の後も 30 分完了しない（`codex-wait` が PENDING で終わった）

## 11. 完了報告（短く）

